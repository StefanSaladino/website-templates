## 3. New creative and architectural contract

**The product moves through one editorial environment, not through a series of independent webpage boxes.**

Preserve SHIFT's original identity, fictional product, artwork ownership, local-only assets and working material choices. Redesign composition instead of piling on more CSS overrides. One real mesh, one renderer and one authored scene coordinate system. The complete stage owns the background, decorative type, readable HTML headline/caption, product, light/environment, and compositional foreground layers. These share the same presentation progress. No separate floating canvas over a normal long-form page, no opaque sticky product-only strip, no per-section reparent/nearest-slot switch, no fade-to-zero teleport, no endless spinning, no scroll capture.

Preferred architecture: bounded cinematic introduction with native document scroll travel; only the complete composition may be sticky inside a story container, with clear start/end and normal unpinned navigation/footer. A single stage can hold all meaningful motion beats; the remainder of the site (material options if necessary, everyday details, CTA) is normal in-flow editorial content, with intentional static product imagery where useful. Do not extend a fixed object across the entire ordinary page. On phones design a portrait composition with headline, card and backdrop together; use a shorter bounded story travel and release to normal content. If a screen is too short or accessibility/graphics constraints prevent a coherent composition, serve an equivalent full in-flow static sequence instead of a persistent viewer. Prove portrait layout and short landscape independently before committing to the exact pin duration.

Proposed structural split (validate in prototype):
- `story-layout.js`: measured stage box, safe text/control zones, responsive geometry, bounded native scroll mapping, anchor/reading-position preservation.
- `story-timeline.js` or replacement `timeline.js`: normalized physical scroll-distance keyframes with continuous position, quaternion rotation or equivalent tested orientation interpolation, camera focal length/distance, scale, lighting, backdrop and text timing. Scene state drives CSS custom properties on stage only.
- `scene.js`: keep compatible renderer public API where feasible; true world-space transform, coherent perspective/light/shadow, projected mesh bounds, controlled material response; scene rendering does not decide page layout or chapter state.
- `script.js`: single frame scheduler, no perpetual idle, bounded time-based smoothing applied to shared presentation state; use actual stage dimensions not repeated per-frame layout reads, handle resize/visibility/restoration, stable semantics. Text that conveys essential information remains DOM, accessible and readable. Do not hide it behind a canvas or create duplicate screen reader headings.
- Rework `index.html` and consolidate `styles.css` after visual prototype acceptance; separate static/responsive layout from effects, remove obsolete P1–P7 conflicting overrides. Fallback must keep same reading order and close geometry; don't insert a large sticky header after initial paint. Preserve focus and scroll anchor if modes differ.

## 6. Revised acceptance and evidence protocol

Functional gates retained: local assets, native scroll, no external runtime, no per-frame idle draw loop, context loss recovery, all controls accessible, original material stills, no horizontal overflow. Budgets retain <=2MB initial transfer, <=300KB added compressed JS and <=2.5M desktop / <=1.25M compact drawing buffer; measure candidate, not prior revision. Frame cadence: aim for 60fps representative desktop and >=30fps representative mobile, measure actual frame intervals and dropped frames under real scrolling; report device/browser, resolution and method, p50/p95 and long-frame counts; do not confuse CPU submit time with FPS. Avoid blanket claims from SwiftShader.

Visual review checklist (every item must pass with actual screenshots AND motion evidence):
1. The opening has a single identifiable visual idea; product, typography and environment feel intentionally composed together. No product-only header. Readable h1 and principal action on first meaningful screen.
2. Object shows purposeful screen-space travel, scale and orientation changes, visible during every transition, no teleport/fade trick, no abrupt scale caps or constant idle spin. Measure projected center/size and orientation for small scroll increments; continuity bounds must not incentivize near-stationary motion. Define target ranges from approved storyboard before code.
3. Heading/caption/backdrop and light advance with the same presentation timeline. No arbitrary independent bands behind the object. Product never passes through navigation, chapter labels, body text or controls. Deliberate overlap is limited to nonessential visual layers.
4. Art-directed entrance and exit; single composition releases from scroll when narrative ends. No card floating over subsequent normal content.
5. Material chapter looks demonstrably different in scale, angle, light and visual purpose; all material changes remain identifiable. Product is grounded in its visual world.
6. Motion tested forward/reverse, at slow and fast native scroll, fast direction change, chapter jump, resize/orientation, background/restore, still and reduced-motion. Compare dense recordings; no visually perceptible snaps, unintended clipping or lag between product and copy.
7. Evidence at 320×740, 390×844, 768×1024, 844×390, 1440×900, 1920×1080, plus physical device recordings where possible. Capture initial frame, every 5% of travel, every intentional transition, final stage release, static fallback; capture motion at real playback rate. Review full frames, not just canvas crops.
8. Keep factual statuses separate: source implemented, numeric checks pass, browser checks pass, visual review passed, physical-device acceptance, stakeholder approval. Record blockers; never silently equate one with another.
